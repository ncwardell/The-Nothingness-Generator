# Topic Template

*Template for a topic file in any experiment's construction chain.*

---

This is the canonical structure of a single topic file. Each topic is one atomic move in an experiment's chain. Following this template keeps the chain auditable and the discipline visible.

## Required structure

```markdown
# [Number]. [Topic name]

> **[One-line statement of what this topic generates or articulates.]**

---

## Question

[The question that birthed this topic. What did prior topics raise that this topic answers?]

The question makes the chain forward-driven: each topic answers a question that arose from prior topics. This articulation prevents retrospective justification and keeps the unfolding empathic — sitting in the prior level and asking what it requires.

## Dependencies

- [Links to prior topic files that this builds on]
- [Links to framework structures (postulates, grammar, process) the topic engages]

If this is the first topic in a chain, say so explicitly.

## Commitment

State **the one commitment** the topic makes (if any). Each topic has at most one commitment, and that commitment cascades through all four standing properties — its polar partner, closure-respecting form, etc., are forced, not separately committed.

If the topic is forced (no commitment), say "None. [Topic] is forced."

If a commitment exists, defend it on minimality grounds (atomicity flavor: algebraic, topological, logical, etc.).

## Construction

The actual move. Trace step by step:

- What the prior commitments and dependencies provide.
- What the move adds.
- What is forced as a consequence.

Each step labeled forced, chosen-with-reasons, or theorem (when appropriate). No skipping levels.

## All four standing properties respected

Every topic must verify all four:

- **Conservation** ($\Sigma = 0$): how the move preserves the conservative sum.
- **Polarity**: how polar partners are handled (forced, not separately committed).
- **Closure**: how new structure stays within the totality (or extends it internally via self-reference).
- **Self-Reference**: how the move respects internal observation / articulation.
- **Internality of Relations**: how relations are internal.

If a move violates any of the four, it is invalid.

## Comparison

How the result aligns with established knowledge in the domain (mathematics, physics, etc.). Be honest:

- Hits: established results that match.
- Novel structural reframings: where the framework's articulation differs in framing but agrees in content.
- Disagreements: if any, flag them clearly.

## Transferability

**Engages:** which framework structural features (postulates, grammar) the topic engages.

**Prediction:** what other lenses (experiments) engaging the same features should articulate. The structural prediction; specific articulations vary by lens.

See [`15-cross-domain-analysis/transferability.md`](../15-cross-domain-analysis/transferability.md).

## What this enables

Pointer to the next topic that builds on this. Make the chain explicit.
```

## Discipline checklist

Before publishing a topic file, verify:

- [ ] Statement is one line, captures the topic's content.
- [ ] Question is explicit: what did prior topics raise that this answers?
- [ ] Dependencies are linked, explicit, and complete.
- [ ] At most one commitment is made (or none — explicitly state "forced").
- [ ] Commitment, if any, is defended on minimality grounds.
- [ ] Construction is traced step by step, each step labeled.
- [ ] All four standing properties are explicitly checked.
- [ ] Comparison to established knowledge is honest.
- [ ] Transferability prediction is named.
- [ ] Next topic is linked.
- [ ] No retrospective draft commentary ("in an earlier version", "I moved this from", etc.).
- [ ] Authoritative voice — present what is, not how it was developed.

## Polarity discipline (especially important)

When introducing operations, structures, or relations:

- Each operation comes with its **polar partner**, automatically. One commitment introduces both halves.
- Each value comes with its **polar complement**, automatically.
- Each relation must be checked against its polar form (if any).

The framework's [Polarity standing property](../03-the-grammar/02-polarity.md) cascades through every level.

## Closure discipline

When operations produce new values not in the current value system:

- **External posit is forbidden.** Closure forbids "just adding" the value.
- **Internal extension is required.** The new value must be generated by an internal self-referential process.

This is why Fibonacci+Zeckendorf generates the integers in arithmetic — Closure forbids successor's external posit.

## Self-Reference discipline

A topic engages Self-Reference if:

- It references its own structure (a recurrence referencing prior values, an equation defining $x$ in terms of $x$).
- It articulates how the totality refers to itself.

When a topic engages Self-Reference, it is part of how the lens articulates the framework's self-referential structure. This contributes to the lens's bootstrap.

## Internality of Relations discipline

Any relation introduced (equality, ordering, operation, function, mapping):

- Must be defined by internal operations on internal values.
- May not invoke external standards or definitions.

## When to make a new topic

Make a new topic file when:

- A new commitment is being introduced.
- A new structural fact is being articulated.
- A new value, operation, or relation is being added.

Do not make a new topic file when:

- The content is a corollary of existing topics (put it in the relevant existing topic).
- The content is methodological commentary (put it in the experiment's module file or a process document).

## When to use module files vs topics

Use a **module file** (named after the subdomain, like `arithmetic.md`) at the level of:

- A subdomain that other subdomains might import.
- A summary of dependencies, commitments, and what the package produces.

Use **topic files** (numbered, in `construction/`) for:

- The atomic step-by-step construction within a subdomain.

## The bootstrap topic

A bootstrap topic verifies that the unfolded structure (potentially across multiple linked subdomains) articulates the framework's seed in the lens's vocabulary. The bootstrap is the success condition for a self-grounding lens. See [`mathematics/algebra/construction/09-the-bootstrap.md`](mathematics/algebra/construction/09-the-bootstrap.md) for an example.

When several subdomains compose into a self-grounding package (as arithmetic + algebra do), the bootstrap lives in the subdomain that articulates the structural relations — typically the algebraic-style subdomain, since the framework's grammar is itself algebraic in character.

## Numbering

Topics are numbered sequentially: 01, 02, 03, ..., 15. Two-digit prefix to allow for inserting between (e.g., 01a if needed, though prefer renumbering if many insertions occur).

The bootstrap topic is the last one, regardless of total count.

## File naming

`NN-short-descriptive-hyphenated-name.md`.

The name should describe the topic clearly (e.g., `07-fibonacci.md`, `13-the-degenerate-triple.md`).

## Cross-references

When linking to:

- A topic in the same construction chain: `[NN. Name](NN-name.md)` (where NN is the topic number, e.g., `07-fibonacci.md`).
- A topic in a different subdomain: relative path through the parent.
- A framework structure: relative path to the structure's file.

Always verify links resolve.

## Status of this template

This template was developed during the arithmetic experiment. It is provisional — adjustments may be needed when applied to different domains. Specific to arithmetic was the use of "construction" as the subfolder name; other lenses may need different organizing structures.

The template's core (one commitment, four-property check, comparison, transferability, what-this-enables) is general. Adjust other elements as the lens requires.
