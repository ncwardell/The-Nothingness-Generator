# Methodology for Cross-Domain Analysis

*How to do this honestly.*

---

## The reframe to keep in mind

Each experiment is the generator articulating itself through a specific lens. Cross-domain analysis is not external comparison of tool-performance across substrates; it is examination of the generator's various self-portraits to identify what persists across all of them.

This reframe matters methodologically: when we look for "patterns across experiments," we are looking for invariant features of the generator that show up regardless of which lens is used. Lens-specific features tell us about the lenses, not about the generator. Confusing these is the source of most cross-domain errors.

## The trap: false convergence

Three sources of false convergence:

### 1. Vocabulary convergence

Experiments use the same word with different structural meanings. "Polarity" in physics may be a quantum-mechanical sign, in language a binary opposition, in biology a chemical asymmetry. The lexical match is not a structural match. Real cross-domain convergence requires *structural identity*, not just shared vocabulary.

### 2. Self-selection

If all experiments are run by experimenters with the same implicit commitments, the experiments will converge on those commitments — not because the generator forces them, but because the experimenters do. The convergence is in the experimenters, not the totality. Real cross-domain evidence requires experiments using *genuinely different commitment chains*, ideally by different experimenters who don't share starting biases.

### 3. Confirmation bias

Looking for what one expects to find and stopping when found. Real cross-domain analysis requires looking for what one *didn't* expect.

## The discipline

For any candidate cross-domain pattern:

1. **State the pattern structurally.** Without using vocabulary specific to any one experiment.
2. **List the experiments where it appears.** With references to specific commitments and assignments in each.
3. **Identify shared commitments across these experiments.** Did the experiments start from compatible positions? If yes, the convergence may be in the starting positions, not in the totality.
4. **Identify distinct commitments across these experiments.** If experiments with very different commitments still produce the pattern, that's stronger evidence.
5. **Try to construct a counter-experiment.** A specific commitment chain in a specific lens where the pattern *should* appear if it's structural — but doesn't. If you can construct one and the pattern is absent, the pattern is conditioned on something we haven't yet identified.

## Strength of evidence

| Strength | Description |
|---|---|
| **Anecdotal** | Pattern in 1–2 experiments. Not yet sufficient evidence. |
| **Suggestive** | Pattern in 3+ experiments using different commitment chains. Worth tracking; not yet load-bearing. |
| **Strong** | Pattern in 5+ experiments using genuinely different chains; surprises the experimenters; resists construction of counter-experiments. |
| **Promoted** | Pattern judged structural enough to update the framework's grammar, postulates, or operating principles. Requires deliberation and explicit framing. |

A pattern at *Promoted* level moves from this section into the strict framework. Until that movement, the pattern lives in [`candidate-refinements.md`](candidate-refinements.md).

## What promotion looks like

1. Pattern is consistently observed at strength ≥ Strong.
2. The pattern is shown to be derivable from the postulates plus some named additional commitment that itself appears across experiments.
3. The framework decides one of:
   - **Promote the commitment to a new postulate** — rare; requires very strong evidence and deliberation about whether the existing three postulates were actually minimal.
   - **Promote the commitment to a new framework-level operating principle** alongside the existing five.
   - **Add a new standing property to the grammar** if the pattern is shown to be forced at the postulate level (with the new derivation made explicit).
   - **Refine an existing property or principle** if the pattern reveals that an existing item was incomplete or imprecise.

Promotion is not a default. Most cross-domain patterns will turn out to be *suggestive but not forced* — interesting but not load-bearing. That's fine. The grammar is meant to be small; promotion is for genuinely structural insights.

## What rejection looks like

A candidate pattern is rejected when:

- It turns out to be self-selection or vocabulary convergence on closer analysis.
- A counter-experiment is constructed and the pattern fails to appear.
- The pattern is shown to be a consequence of incidental commitments rather than the postulates or any well-traveled commitment.

Rejected patterns are documented briefly in [`observations.md`](observations.md) so they don't get re-discovered as candidates later.

## Reading note

Cross-domain analysis is the framework's empirical research program. It is the place where the framework grows or proves limited based on what experiments actually produce. This section is meant to be active and ongoing, not finalized. The discipline above keeps it from becoming a confirmation-bias fest.

The user of this discipline should expect to reject far more candidates than they promote. A framework that grows quickly through cross-domain "discoveries" is most likely growing through bias. A framework that grows slowly and selectively, with rigorous distinguishing of structural-from-incidental, is doing the work honestly.
